How detection works

Two signals, one pgvector query each

No separate graph database and no separate vector database — AlloyDB's pgvector extension does both the traversal and the similarity math, so each detector below is one SQL query against the live graph.

Signal 01 — Latent collaboration

People who should have met by now

Two researchers with no COLLABORATES_WITH edge and no shared paper, but whose STUDIES_TOPIC / USES_METHOD embeddings land within cosine 0.82 of the same node cluster — surfaced as an introduction worth making.

SELECT a.person_id, b.person_id FROM person_topic a JOIN person_topic b ON a.topic_id = b.topic_id AND a.person_id < b.person_id WHERE NOT EXISTS (...COLLABORATES_WITH...) GROUP BY a.person_id, b.person_id HAVING COUNT(*) >= 2;

Signal 02 — Redundant effort

Studies running in parallel, unaware

Two Paper/Repository nodes whose full-document embeddings are highly similar, but with no CITES edge between them — a candidate duplicate worth a five-minute human check before more budget goes in.

SELECT a.id, b.id, 1-(a.embedding<=>b.embedding) sim FROM node a JOIN node b ON a.node_type = b.node_type AND a.id < b.id WHERE 1-(a.embedding<=>b.embedding) > 0.82 AND NOT EXISTS (...CITES...) ORDER BY sim DESC;

Under the hood

Portal to graph in one streaming pipeline

Three stateless Cloud Run services, wired by Eventarc and Pub/Sub, writing into a single AlloyDB instance. Nothing to keep in sync, nothing that doesn't scale to zero between ingests.
